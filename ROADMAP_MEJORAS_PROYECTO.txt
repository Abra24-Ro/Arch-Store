# ROADMAP DE MEJORAS DEL PROYECTO

## 1. Objetivo general del roadmap

El objetivo es mejorar el proyecto de forma progresiva, segura y educativa, usando el e-commerce como laboratorio full stack/backend.

La prioridad no será agregar features nuevas, sino fortalecer fundamentos reales: autorización, seguridad en Server Actions, manejo correcto de sesión, validaciones, tipado, consistencia de datos, testing, control de stock, pagos y despliegue responsable en Vercel.

Al finalizar este roadmap deberías entender mejor:
- Cómo proteger operaciones del servidor.
- Cómo separar autenticación de autorización.
- Cómo validar datos antes de tocar la base de datos.
- Cómo trabajar con ramas sin romper main.
- Cómo probar manualmente cambios críticos.
- Cómo mejorar un proyecto existente sin perderte agregando features sin propósito.

## 2. Reglas de trabajo con Git y Vercel

main debe mantenerse estable porque está conectado a Vercel y hace deploy automático.

Cada mejora debe hacerse en una rama separada. No se debe trabajar directo sobre main.

Nombres sugeridos de ramas:
- fix/week-01-admin-server-actions-auth
- fix/week-02-user-session-ownership
- chore/week-03-routes-env-cleanup
- refactor/week-04-zod-error-handling
- refactor/week-05-auth-prisma-types
- feature/week-06-admin-server-pagination
- fix/week-07-privacy-logs-cleanup
- test/week-08-core-unit-tests
- fix/week-09-stock-transactions
- refactor/week-10-paypal-order-status

Flujo recomendado, solo como ejemplo:

git checkout main
git pull origin main
git checkout -b fix/admin-server-actions-auth

git status
git add .
git commit -m "fix: protect admin product server actions"
git push origin fix/admin-server-actions-auth

Cuándo hacer commit:
- Cuando una mejora pequeña esté completa.
- Cuando la app siga funcionando.
- Cuando el cambio tenga un propósito claro.
- No mezclar varias semanas en un solo commit.

Cuándo hacer merge a main:
- Solo después de probar manualmente.
- Solo después de revisar el diff.
- Solo si no hay archivos modificados innecesarios.
- Solo si entiendes qué cambió y por qué.

Qué verificar antes de mergear:
- Login funciona.
- Catálogo funciona.
- Carrito funciona.
- Checkout no se rompe.
- Admin funciona si aplica.
- No hay secretos expuestos.
- No hay errores visibles en consola.
- Vercel debería poder desplegar.

Qué hacer si Vercel falla después del merge:
- No seguir agregando cambios.
- Revisar logs de Vercel.
- Identificar el commit que rompió el deploy.
- Crear una rama de fix desde main.
- Si el error es grave, revertir el merge con un commit de reversión.

Cómo documentar cada mejora:
- Escribir qué problema se resolvió.
- Qué archivos se tocaron.
- Qué aprendiste.
- Qué pruebas manuales hiciste.
- Qué quedó pendiente.

## 5. Flujo de trabajo semanal recomendado

Cada semana puede trabajarse en bloques de 1 hora.

Día 1: Lectura del problema y documentación.
- 20 min: leer el punto del roadmap.
- 20 min: leer documentación.
- 20 min: escribir qué entiendes y qué dudas tienes.

Día 2: Explorar código relacionado.
- 20 min: abrir archivos principales.
- 20 min: seguir el flujo de datos.
- 20 min: anotar dónde está el riesgo.

Día 3: Diseñar solución en notas.
- 20 min: escribir solución ideal.
- 20 min: reducirla a un cambio pequeño.
- 20 min: definir pruebas manuales.

Día 4: Implementar cambio pequeño.
- 45 min: tocar solo archivos necesarios.
- 15 min: revisar diff.

Día 5: Probar manualmente.
- 20 min: probar flujo feliz.
- 20 min: probar usuario sin permiso.
- 20 min: probar caso borde.

Día 6: Refactorizar si es necesario.
- 30 min: limpiar duplicación.
- 15 min: revisar nombres.
- 15 min: preparar commit.

Día 7: Merge a main solo si todo está correcto.
- 20 min: revisar checklist.
- 20 min: merge.
- 20 min: revisar deploy de Vercel.

## 7. Criterios para pasar una rama a main

- La app corre localmente.
- No hay errores visibles en consola.
- El flujo principal sigue funcionando.
- Login funciona.
- Logout funciona.
- Catálogo funciona.
- Detalle de producto funciona.
- Carrito funciona.
- Checkout funciona.
- Admin funciona si aplica.
- Usuario normal no puede ejecutar acciones admin.
- No hay secretos expuestos.
- No se modificaron archivos innecesarios.
- No se mezclaron mejoras no relacionadas.
- El commit tiene mensaje claro.
- Se revisó el diff antes de mergear.
- Se entiende qué se aprendió con el cambio.
- Vercel debe quedar verde después del merge.

## 8. Conclusión

Lo primero que deberías priorizar es seguridad del servidor: autorización en Server Actions, uso correcto de sesión y propiedad de datos. Eso te va a dar una base profesional mucho más fuerte que agregar features nuevas.

Todavía no conviene tocar features grandes como favoritos, cupones o filtros avanzados. Antes vale más entender bien auth, permisos, validación, errores, stock y pagos.

Para evitar perderte agregando features, cada rama debe responder una pregunta concreta: ¿qué problema mejora?, ¿qué habilidad aprendo?, ¿cómo pruebo que no rompí nada?

Este proyecto puede ser un laboratorio serio si lo trabajas con calma: una semana, una mejora, una rama, un aprendizaje claro. Así dejas de “seguir el curso” y empiezas a pensar como desarrollador full stack responsable.
